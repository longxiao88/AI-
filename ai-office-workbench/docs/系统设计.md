# 系统设计

本文按当前源码说明系统结构，涉及的文件路径都可以在项目里直接找到。

## 1. 总体架构

```text
 浏览器（React 单页应用，src/）
   │  fetch /api/...（JSON，Cookie 会话）
   ▼
 Node.js 进程（server/，Express 5，只监听 127.0.0.1）
   ├─ 本机访问保护 → 登录校验（账号隔离）→ 参数校验（Zod）
   ├─ 业务接口：记录 / 项目任务 / 知识库检索 / 操作日志 / 设置
   ├─ AI 接口 ──────────────► 模型服务（OpenAI 兼容 /chat/completions）
   │                            API Key 只在进程内存
   ├─ 邮件接口 ────────────► SMTP 服务器（账号找回 / 邮箱验证码）
   │                            授权码：环境变量优先，否则加密入库
   └─ SQLite（node:sqlite，data/workbench.sqlite）
 shared/：前后端共用的类型、AI 结构校验、知识库检索、日志差异计算
```

生产模式下前端先构建到 `dist/`，由同一个 Node 进程提供页面和接口，只需一个端口（默认 4318）。开发模式 `npm run dev` 同时启动后端和 Vite（5178），Vite 把 `/api` 转发到 4318。

### 2.1 模块之间的内容流动

有几处功能让内容可以在模块间搬运，它们的共同点是**复用已有的记录接口、零后端改动**，并且都遵循「先出草稿 / 先勾选，确认后才写入」的一贯做法：

| 从 | 到 | 实现方式 |
| --- | --- | --- |
| 知识库页上传的文本文件 | 知识库表单 | `FileReader` 前端解析，只填表单不入库 |
| 会议待办的文本行 | 项目任务看板 | 按行拆分去重后，走 `POST /projects/:id/tasks/batch` |
| 写作结果 | 知识库条目 | `POST /entries/knowledge` |
| 整段问答对话 | 知识库条目 | `POST /entries/knowledge` |
| 文档原文 | 工程导图 / 分析笔记 | `POST /ai/mindmap` 出结构，前端布局渲染 |

「全局搜索」页则相反：它不新增后端接口，而是拉取一次 `GET /entries`（服务端已按账号过滤），在前端做跨模块的关键词匹配与片段摘录。

### 2.2 界面动效

四处常驻动效都由 `<html>` 上的两个属性驱动：`data-theme`（`dark` / `light`）和 `data-motion`（`on` / `off`）。关闭动效开关或系统开启「减少动态效果」时，只需把 `data-motion` 置为 `off`，全部动效停止，功能不受影响。

| 动效 | 实现位置 | 说明与降级 |
| --- | --- | --- |
| 背景气泡 | `src/components/BubbleBackground/` | Canvas 逐帧绘制「深海气泡」款式：径向渐变 + 描边 + 左上双高光，分大/中/小三层尺寸自下而上漂浮、飘出顶部后回收；监听 `data-theme` 切换两套配色、`data-motion` 暂停；画布按设备像素比放大但不超过 2 倍；组件卸载时断开 MutationObserver 并销毁绘制循环；画布是 `pointer-events: none`，点破事件挂在 `window` 上并过滤按钮 / 链接 / 输入框，命中判定 `距离 < 半径 × 2 + 12`，破裂后按母泡半径分裂 2–8 个子泡、生成 12–21 颗水雾与 1 个核心闪光，总数上限 260 防止连点爆炸 |
| 鱼群背景 | `src/components/FishBackground/` | Canvas 绘制的**五色鱼群**：按颜色分成 5 群、每群 5 条（总数按屏幕面积 ÷ 52000 计算，限定 20–42）；鼠标移动时只牵引「头鱼离鼠标最近」的那一群，其余群各自漫游。群内头鱼 = 该群中离目标最近的一条（1.3 倍滞回防抖），每 5 帧重算一次**前驱树**：每条鱼跟同群中比自己更靠近目标、且离自己最近的同伴，前驱超过 95px 就直接跟头鱼（避免串成长龙）；间距 52px、阻尼 0.99、限速 0.35–2.4、朝向以 0.1 的系数追赶速度方向。鼠标静止 1.2 秒且该群 60% 的鱼进入 150px 内则自动解除牵引。**允许游出画面**：不设边界力，只剩不到 55% 的鱼在屏幕内时，把画面外的鱼从随机一侧边缘送回（屏幕内的鱼不受影响）。透明度按离目标远近递减 × 正弦呼吸；鱼身是胖锦鲤（贝塞尔鱼身、分叉尾鳍、背鳍、眼睛），尾鳍按相位轻摆；颜色按群取，深 / 浅主题各一套；与气泡共用 `data-theme` / `data-motion` / 主题揭幕的生命周期 |
| 场景轮播 | `src/components/SceneCarousel.tsx` | 四张场景图按 5 秒间隔循环，切换方式是**擦除翻页**：两层叠放，上层是当前图，遮罩渐变压到 200% 宽后用 `mask-position` 从 0% 推到 100%（渐变本身不能插值，只有位置能），图片本身不位移；擦除边界是硬切换（50% 处阶跃），两层不重叠、不会互相透出；左侧渐隐（8% → 55% 跨度，右侧 45% 保持原色）加在视口这一层，而不是每张图上，否则上层半透明会让下层透出来；动画 1.5 秒，换图那一帧禁用过渡让遮罩瞬间归位，否则新图会淡入一遍；往左拖 = 当前图从右往左被擦掉（看下一张），往右拖相反；拖动时擦除进度跟手，松手超过 18% 完成切换，否则回弹；悬停、键盘聚焦、`document.hidden`、离开视口时暂停，下一张加载完成前不自动切换；底部胶囊指示器，当前项拉伸成 22px 白条；统一 `object-fit: cover` 铺满（工作台从卡片 43% 处开始，给左侧文案让位） |
| 卡片流光 | `src/components/LightFrame.tsx` | 纯装饰，`aria-hidden` 且不响应鼠标事件；离开视口或页面隐藏时停止 |
| 主题揭幕 | `src/lib/themeTransition.ts` + `src/style.css` | 见下 |

主题揭幕的流程（`src/lib/themeTransition.ts`）：

1. 调用 `document.startViewTransition(update)`，浏览器为切换前后各截一张快照。
2. `update` 必须**同步**把新主题写到 DOM 上（`flushSync` + `document.documentElement.dataset.theme`），否则浏览器会截到旧主题。这是全站唯一必须同步写入 DOM 的场合。
3. `transition.ready` 之后，对 `::view-transition-new(root)` 这个伪元素做 `maskPosition` 关键帧动画，把带羽化的渐变遮罩自下而上推过去；遮罩本体定义在 `src/style.css`（`mask-size: 100% 200%`，上端实心、下端渐隐）。
4. 起点 `50% -24%` 时羽化带最淡的一端刚好落在屏幕底边，屏幕上还看不出新主题；终点 `50% 100%` 时实心段铺满整屏。
5. `transition.finished` 的 reject 被吞掉，连续点击导致上一次过渡被跳过时不会产生未捕获异常。

不支持 View Transitions 的浏览器、关闭动效、系统开启「减少动态效果」三种情况都直接走瞬时切换，不做任何动画。

### 2.3 工程导图的布局

导图采用「横向树」布局：根在左、层级向右展开。布局逻辑全部集中在 `src/lib/mindmap.ts`，是**不依赖 React 与 DOM 的纯函数**，因此可以脱离浏览器直接跑单元测试，页面展示与导出的 SVG 也共用同一套坐标，不会出现「页面上对、导出错位」的问题。

规则如下：

- 每一层占一列，列宽按**该层最宽节点**的实际文本宽度计算（而非固定值），层与层之间结构性不重叠。
- 叶子节点在列内依次堆叠；父节点相对首尾子节点的垂直中线居中，并带同层防撞下限。
- 画布尺寸完全由内容决定，不再是写死的固定值。

> 早期实现用 `x = depth * 70` 计算列位置，而节点框宽 150px，相邻层级必然互相遮挡；画布宽写死 900 又会造成导出图大片空白。这两点已通过上面的按内容计算修正，并补了 5 组回归测试。

## 3. 数据库

| 表 | 主要字段 | 说明 |
| --- | --- | --- |
| entries | id, **accountId**, kind, title, data(JSON), createdAt, updatedAt | 五类记录共用，kind 区分模块；各模块字段放在 data 里 |
| tasks | id, **accountId**, projectId, title, status | 项目任务，projectId 外键指向 entries，删除项目时级联删除；status 只能是 todo / doing / done |
| request_batches | requestId, **accountId**, projectId, titles, taskIds, createdAt | AI 批量加入任务的去重记录 |
| audit_logs | seq, id, **accountId**, payload(JSON) | 操作日志，payload 含动作、标题、每行的变更前后内容 |
| settings | **accountId**(主键), baseUrl, model | 模型地址与名称，**按账号保存**；不存 API Key |
| account | **id**(=用户名, 主键), username, passwordHash, salt, profile(JSON), email, emailVerified | 多账号，一行一个账号 |
| sessions | tokenHash(主键), accountId, expiresAt | 登录会话，只存令牌的 SHA-256，绑定到具体账号 |
| app_config | key(主键), value | 全局应用级配置（服务级，非按账号）；目前只有 `key="smtp"` |
| password_resets | tokenHash(主键), accountId, email, codeHash, attempts, expiresAt | 找回密码 / 邮箱绑定的验证码记录，只存哈希 |

数据库开启外键和 WAL 模式。data 字段示例：写作 `{mode, input, output}`，会议 `{date, source, summary, todos}`，项目 `{description}`，文档 `{source, notes}`，知识库 `{source, keywords}`。

**索引**：`idx_entries_account(accountId, kind)`、`idx_tasks_account(accountId)`、`idx_audit_account(accountId)`。

> 索引不能写进建表语句里。旧库升级时表上还没有 `accountId` 列，直接 `CREATE INDEX` 会报 `no such column`。因此索引统一放在 `ensureIndexes()` 中，在迁移完成之后再创建。

### 3.1 多账号的数据隔离

业务表都带 `accountId`，服务端在每个 `/api` 请求上挂载当前登录账号 ID（`accountOf(req)`），所有读写都以它作为过滤条件。隔离在服务端完成，前端改参数也绕不过去。

需要留意的一处细节：`/api/entries/:id` 这类接口在查找记录时同时匹配 `id` 与 `accountId`，因此拿别的账号的记录 ID 也读不到，返回 404 而不是 403 —— 不泄露「该 ID 存在」这一信息。

### 3.2 从单账号升级的迁移顺序

旧版本是单账号结构（`account` 表固定 `id=1`，业务表没有 `accountId`）。升级时会自动迁移，顺序如下：

1. `createStore()` 建表（带 `accountId` 的新表结构用 `CREATE TABLE IF NOT EXISTS`，旧表已存在则原样保留）。
2. `installAuth()` 建 `account` / `sessions` / `password_resets` 表。
3. `migrateLegacyAccount()`：若 `account.id` 还是整数类型，重建为文本主键结构，用用户名作主键，原账号保留。
4. `migrateLegacySessions()`：旧 `sessions` 表缺 `accountId`，直接重建（会话是临时数据，丢弃无影响）。
5. `migrateAccountEmail()`：给 `account` 补 `email` / `emailVerified` 字段。
6. 若 `entries` 表缺 `accountId` 且已有账号，调用 `migrate(db, 第一个账号)`：给四张业务表补列并把存量数据全部归入第一个账号；`settings` 表主键从 `id=1` 改为 `accountId`，原值一并搬迁。
7. `ensureIndexes()` 建索引。

全新安装的数据库表自带 `accountId`，第 3–6 步都会直接跳过。

## 4. 保存与操作日志

所有写操作都经过 `store.audit()`（server/db.ts）：

1. `BEGIN IMMEDIATE` 开启事务，读取变更前快照（当前账号的全部记录和任务）。
2. 执行写入，再读取变更后快照，用 `shared/audit.ts` 的 `difference()` 对比出增、改、删的行。
3. 有变化才写一条日志，然后提交；任何一步出错整体回滚，数据和日志不会不一致。

快照与日志都按 `accountId` 取，所以操作日志也是各账号独立的，回溯不会影响其他账号。回溯时先检查日志涉及的每一行当前是否仍等于当时的「变更后」内容，被后续操作改过就返回 409，要求先回溯较新的操作；还会检查恢复后不出现没有项目的任务。回溯本身也记一条日志。

## 5. AI 请求流程

```text
页面点「生成」 → 前端禁用保存与重复点击 → POST /api/ai/...
  → 登录与参数校验（原文 ≤ 20,000 字，超出返回 400，不截断）
  → 互斥检查：已有 AI 请求在处理则 409
  → 组装 system 提示词 + 用户内容 → 模型服务（60 秒超时，不重试）
  → 写作 / 知识库 / 问答：直接返回文本
    会议 / 项目 / 文档 / 工程导图：解析 JSON 并按结构校验，不符合返回 502
  → 前端显示为可编辑草稿（此时不写数据库）
用户编辑草稿 → 应用到表单 → 点「保存」→ PUT /api/entries/:id → 事务 + 操作日志
```

- 会议、项目、文档、工程导图把用户内容以 JSON 字段发给模型，提示词声明其中的指令一律当作资料，降低提示词注入风险。模型返回允许外层包一层 ```json 代码块，其余格式一律按错误处理，不猜测修补。
- 工程导图的结构是**递归树**（`mindmapNodeSchema` 用 `z.lazy` 自引用），节点文本 ≤120 字、每层子节点 ≤12 个；深度不限，但受模型输出长度与 20,000 字输入上限约束。
- 项目拆解去掉完全重复的任务名；批量加入时前端生成 requestId，同一批重复提交返回上次结果（200），同号不同内容返回 409，已被回溯撤销的批次不会假装成功。
- 知识库问答先用关键词检索，最多取 5 条、每条 900 字摘录交给模型并要求标注来源编号；没有命中直接返回 404，不调用模型。
- 独立问答由前端带上整段对话（最多 39 条消息、总计 40,000 字、必须一问一答交替并以提问结尾），服务端不保存；客户端不能提交 system 角色。
- 写作、知识库、问答的提示词要求纯文本输出，因为结果显示在纯文本区域并可导出 TXT。
- AI 请求是**全局串行**的（不区分账号），处理期间记录当前账号，用于错误归属；请求进行中不允许任何账号修改设置。

## 6. 认证与安全

**账号与会话**

- 多账号：一个工作空间可注册多个账号，账号名全局唯一。密码用 scrypt + 随机盐哈希保存。
- 登录校验失败时也执行一次哈希运算，避免从响应时间判断账号是否存在；同一来源连续失败 10 次锁定 15 分钟。
- 会话：登录后下发 32 字节随机令牌，Cookie 设置 HttpOnly、SameSite=Strict，有效期 7 天；数据库只存令牌的 SHA-256，且绑定 `accountId`。退出时删除该条会话。
- 重置密码成功后会清空该账号的全部会话，防止旧会话继续可用。

**找回密码与邮箱绑定**

- 验证码 6 位数字、5 分钟有效、最多尝试 5 次，数据库只存 SHA-256 哈希；比较用 `timingSafeEqual`。
- 防账号枚举：请求验证码时，账号不存在或未绑定邮箱一律静默返回成功提示，只看返回文案区分不出来。
- 邮箱唯一：一个邮箱只能绑定一个账号。
- 发送邮件前必须先通过验证码验证，验证通过才写入 `account.email`。

**访问范围**

- 服务只监听 127.0.0.1；`/api` 请求的 Host 必须是本机地址（防 DNS 重绑定）；写请求拒绝跨站 Origin 和 `Sec-Fetch-Site: cross-site`，并要求 JSON 内容类型。

**凭据保护**（两种凭据的处理方式不同，这是有意设计）

| 凭据 | 存储方式 | 原因 |
| --- | --- | --- |
| AI 的 API Key | **只存进程内存**，不落盘，重启即清空 | 每次运行手动填写，风险窗口最小 |
| SMTP 授权码 | 环境变量优先；否则 **AES-256-GCM 加密**后入库 | 邮件服务需在无人值守时也能发信（如账号找回），不能只靠内存 |

SMTP 授权码的保护细节（`server/secrets.ts` + `server/smtp.ts`）：

- 加密算法 AES-256-GCM，密文格式 `enc:v1:<iv>:<authTag>:<密文>`，带认证标签，**被篡改时解密会失败**而不是返回错误内容。
- 密钥为 32 字节随机数，存放在数据库同目录的 `.mail-key`（权限尽量设为 0600），**与数据库文件分离**。单独复制数据库文件拿不到密钥，无法还原授权码。
- 读取时自动兼容旧版本遗留的明文；启动时 `migrateSmtpSecret()` 会把明文就地改写为密文，不影响正常发信。
- 接口只返回 `configured` 布尔与 `managedByEnv` 标记，**任何情况下都不返回授权码本身**（包括走环境变量时）。
- 更彻底的做法是直接用环境变量 `SMTP_PASS`，那样授权码完全不进数据库，界面上对应表单自动变只读。

> 这是「数据库文件与密钥文件分离」级别的保护，用来防止数据库被顺手复制走，不是对抗已经能读本机磁盘的攻击者。

**其它**

- API 地址必须是 https（本机地址除外），不允许带账号、查询参数或片段；请求模型时禁止重定向。
- AI 处理中不允许修改设置和清除 Key，避免请求中途换连接。

## 7. 错误处理

| 情况 | 状态码 | 提示方式 |
| --- | --- | --- |
| 参数不合法、超长 | 400 | 「输入格式不正确，请检查必填内容及字数限制」 |
| 未登录 | 401 | 「请先登录工作空间」 |
| 账号或密码错误 / 验证码错误 | 401 | 具体提示 |
| 非本机访问、跨站请求 | 403 | 拒绝 |
| 记录、任务或项目不存在 | 404 | 「记录不存在或已删除」 |
| 账号名重复、邮箱已被占用、AI 请求重复、未配置模型或 Key、回溯冲突 | 409 | 具体原因 |
| 验证码已过期 | 410 | 「验证码已过期，请重新获取」 |
| 登录或验证码尝试次数过多 | 429 | 「尝试次数过多，请稍后重试」 |
| 服务商返回 400/401/403/404/429 | 502 | 转换为通用中文提示，不透传服务商原始信息 |
| 模型返回空内容或 JSON 格式不符 | 502 | 提示手动重试 |
| 未配置邮件服务 | 503 | 「发件邮箱尚未配置」 |
| 模型 60 秒未响应 | 504 | 提示超时、输入已保留 |
| 其他异常 | 500 | 「保存或处理失败，请重试」 |

前端失败时只显示提示，输入框、草稿和已保存内容保持原样，不自动重试，也不会用示例内容冒充 AI 结果。

## 8. 演示模式

`npm run build:preview` 使用 `VITE_PREVIEW_MODE=true` 构建。此时前端不访问后端，`src/lib/preview.ts` 用浏览器 localStorage 模拟记录、任务和操作日志接口，自带标注为「示例」的数据；所有 AI、密钥与邮件接口直接返回不可用提示。它只用于展示界面，不代表真实的登录、保存或 AI 能力。

演示模式同样支持多账号：localStorage 按账号名分区存放，切换账号看到的是各自的数据。邮件相关功能在演示模式下不可用。
